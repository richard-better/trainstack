## Affected Pages/Routes

- `POST /rpc/sessions.generateDailySession` — Core happy path, fallback chain, concurrent call deduplication
- `POST /rpc/sessions.generateWeeklyScaffold` — Schedule generation, partial schedule fill, fallback

## Key Interactions to Verify

- App open new day → session_date (local YYYY-MM-DD) sent → server checks sessions table → no row → generates daily session → home shows session card
- App open same day → existing session row found → returns immediately, no AI call
- Session runner: bilateral exercise shows single set block, no side prompt
- Session runner: left_right exercise shows left sub-set, completes, auto-advances to right sub-set
- Exercise advance → AsyncStorage write first, then fire-and-forget server PATCH
- Session completion → feedback_rating stored → capacity_ratings_after stored in capacity_logs
- All-low capacity ratings at intake → rest day screen shown, no session generated (TODO-002)
- Home screen on app reopen mid-session → drop_off_exercise_index read from server + local max → Resume CTA at correct position

## Edge Cases

- Claude API returns malformed JSON → retry at temperature 0.2 → if still bad → hardcoded fallback, is_fallback=true
- Claude API timeout (>10s) or 5xx → hardcoded fallback served immediately
- Exercise name in Claude response not in exercises.ts catalogue → retry → fallback
- Concurrent generateDailySession calls (same user, same date) → UNIQUE constraint → ON CONFLICT DO NOTHING → second call returns existing row
- Duplicate waitlist email → idempotent (no duplicate row)
- Rate limit on waitlist (4th req same IP within 60s) → 429
- Unauthorized access to sessions endpoints → 401
- Session not found for updateProgress → 404
- No scaffold rows for today → generateWeeklyScaffold fires first, then generateDailySession
- Scaffold rows exist for today → generateDailySession uses today's theme, no scaffold regen

## Critical Paths

- New user onboarding complete → weekly scaffold generated → daily session generated → home screen shows session card (E2E)
- Session runner: 5-exercise session completed → feedback submitted → capacity_ratings_after captured → next day generation uses yesterday's feedback + post-session ratings (E2E)
- Claude API degraded on app launch → fallback session served in ≤10 seconds → non-blocking retry banner shown
- Concurrent app opens on same day → exactly one session row per user per date in DB
- Resume path: exit mid-session at exercise 3 → poor connectivity for 60s → close app → reopen → Resume CTA at exercise 3 (local AsyncStorage used as backup)
